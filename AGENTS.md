# AGENTS.md — правила совместной разработки Blue Whale

Этот файл обязателен для чтения любой моделью/ассистентом **до любого изменения проекта**.

## 1. Назначение документа

`AGENTS.md` определяет процесс совместной разработки проекта **Blue Whale**: кто владеет репозиторием, где находится источник истины, в каком порядке читается документация, как делятся работы на спринты и шаги, как готовятся handoff-пакеты и что считается PASS/FAIL.

Этот документ не заменяет техническое задание. Продуктовые требования находятся в `docs/TECHNICAL_SPEC.md`, порядок разработки — в `docs/ROADMAP.md`, текущая рабочая точка — в `docs/PROJECT_STATE.md`.

## 2. Репозиторий и локальная рабочая папка

Основной пользовательский репозиторий:

```text
https://github.com/Lex26p/bluewhale
```

Локальная папка пользователя в Windows:

```text
C:\Projects\bluewhale
```

Ветка по умолчанию на момент основания проекта:

## 3. Источник истины

**Источник истины проекта — актуальное состояние пользовательского репозитория `Lex26p/bluewhale`.**

Перед каждым новым шагом ассистент обязан заново прочитать актуальное состояние репозитория и необходимые для шага файлы. Нельзя продолжать работу только по локальной копии, предыдущему ZIP или старому SHA, если пользователь уже сделал новый commit/push.

Документы читать в следующем порядке:

1. `AGENTS.md` — правила процесса и handoff.
2. `docs/PROJECT_STATE.md` — текущая рабочая точка и подтверждённое состояние.
3. `docs/TECHNICAL_SPEC.md` — продуктовые и технические требования.
4. `docs/ROADMAP.md` — порядок спринтов/шагов и критерии PASS.
5. Только после этого — относящиеся к текущему шагу исходные файлы.

Git history используется для трассируемости и диагностики, но не заменяет чтение актуальных файлов.

## 4. Право на изменения репозитория

### 4.1. Пользователь

Пользователь является единственным владельцем локального репозитория и процесса commit/push.

Пользователь самостоятельно:

- распаковывает handoff ZIP в `C:\Projects\bluewhale`;
- запускает нужные проверки;
- проверяет интерфейс на компьютере и, когда это требуется, на iPad;
- сообщает PASS или присылает замечания/ошибки;
- после PASS выполняет `git add`, `git commit`, `git push`;
- присылает ассистенту новый полный SHA из `git rev-parse HEAD`.

### 4.2. Ассистент

Ассистент **никогда не создаёт, не изменяет, не удаляет, не commit-ит и не push-ит файлы непосредственно в GitHub-репозитории пользователя**.

Даже если технически доступен GitHub write API, для Blue Whale он не используется.

Ассистент использует GitHub только для чтения актуального состояния проекта, после чего:

- готовит изменения в собственной временной рабочей среде;
- выполняет доступные локальные проверки;
- передаёт пользователю финальные файлы через ZIP;
- не передаёт patch/diff как основной способ внесения изменений;
- при FAIL остаётся в текущем шаге и готовит исправление;
- после нового пользовательского SHA заново читает репозиторий.

## 5. Модель разработки: Спринт → Шаг

Разработка разделяется на два уровня.

### Спринт

Спринт — крупная функциональная область разработки.

Основные запланированные спринты проекта:

```text
DOC     — документация и foundation
WEB     — визуальный Web UI без реальной связи с оборудованием
RULES   — WB Rules / автоматизация / виртуальные controls
JS      — JavaScript Web: MQTT, реальное состояние и команды
FINAL   — интеграция и финальная приёмка
```

### Шаг

Шаг — конкретная ограниченная задача внутри спринта.

Пример:

```text
WEB-01 — общая страница
WEB-02 — уставка температуры
WEB-03 — показатели помещения
WEB-04 — общее управление фанкойлами
```

Шаг может иметь несколько итераций. Первая переданная версия не означает PASS.

Обычный цикл:

```text
реализация
   -> пользовательская проверка
   -> замечания
   -> исправление в том же шаге
   -> повторная проверка
   -> PASS
   -> commit/push пользователя
   -> новый SHA
   -> следующий шаг
```

Нельзя переходить к следующему шагу только потому, что текущая версия «почти готова».

## 6. Scope discipline

Перед реализацией каждого шага ассистент явно определяет:

- цель шага;
- какие файлы предполагается добавить/изменить;
- что входит в scope;
- что **не входит** в scope;
- конкретные критерии PASS.

Ассистент не должен молча добавлять задачи будущих шагов «заодно».

Например, во время спринта `WEB` запрещено незаметно начинать реальную MQTT-интеграцию только потому, что кнопка уже существует визуально. В спринте `WEB` допускается только демонстрационное локальное поведение, нужное для оценки UX.

Если новая фактическая информация делает ранее согласованный план неправильным, ассистент должен сначала остановиться, объяснить причину и предложить явную ревизию оставшегося плана.

### 6.1. Принятые решения допускают последующую ревизию

PASS шага или ранее принятое пользовательское решение является актуальной рабочей базой, но **не делает решение навсегда неизменяемым**. Если на более позднем этапе появляется более удачный UX, новая фактическая информация об оборудовании или становится очевидна более простая/понятная реализация, ранее согласованную часть проекта можно изменить.

Такая ревизия должна быть явной: ассистент объясняет, что именно предлагается изменить, почему это лучше и какие уже реализованные части затрагиваются. Нельзя молча ломать ранее подтверждённое поведение под видом несвязанного шага.

Цель процесса — сохранить управляемость разработки, а не искусственно запретить улучшение уже принятого решения.

## 7. Handoff ZIP

Основной способ передачи изменений от ассистента пользователю — ZIP с **финальными файлами**, а не patch/diff.

Пути в архиве идут от корня репозитория.

Правильно:

```text
BLUEWHALE_WEB_01.zip
    index.html
    css/
        app.css
    js/
        app.js
```

Неправильно:

```text
BLUEWHALE_WEB_01.zip
    bluewhale/
        index.html
```

Стандартная распаковка:

```powershell
Expand-Archive `
  -Path "$env:USERPROFILE\Downloads\<PACKAGE>.zip" `
  -DestinationPath "C:\Projects\bluewhale" `
  -Force
```

Если handoff содержит только документацию, структура сохраняет реальные пути репозитория, например:

```text
AGENTS.md
docs/TECHNICAL_SPEC.md
docs/ROADMAP.md
docs/PROJECT_STATE.md
README.md
```

## 8. Проверки и PASS/FAIL

Каждый шаг имеет собственные PASS-критерии.

Общее правило:

- `PASS` — пользователь подтвердил критерии шага;
- `FAIL` — хотя бы один обязательный критерий не выполнен;
- при FAIL commit не выполняется и следующий шаг не начинается;
- исправление должно быть минимально направлено на текущий FAIL, если нет причины пересматривать scope.

Документационный commit сам по себе не подтверждает будущую функциональность оборудования.

Например, наличие кнопки «Вентиляция» в HTML не означает, что вентиляция интегрирована с Wiren Board.

## 9. Git после PASS

После пользовательского PASS:

```powershell
Set-Location C:\Projects\bluewhale

git add .
git status --short
git commit -m "<meaningful commit message>"
git push

git rev-parse HEAD
```

Пользователь присылает новый полный SHA ассистенту.

Следующий шаг начинается только от актуального состояния репозитория после этого commit/push.

## 10. Development environment

Blue Whale не является C++-проектом и не требует Linux build toolchain.

Основная development environment:

```text
Windows
C:\Projects\bluewhale
HTML / CSS / JavaScript
обычный современный browser
```

### WSL

WSL **не требуется** для текущей архитектуры проекта и не должен добавляться в workflow без новой явной технической необходимости.

### Node.js / npm

Проект не должен зависеть от Node.js/npm как обязательного runtime или build step, если это отдельно не согласовано в будущем.

Цель — статический Web, который может быть установлен на Wiren Board и работать без внешнего интернета.

### Docker

Docker не является частью build/runtime/deployment архитектуры Blue Whale.

## 11. Web и offline-first

Основной пользовательский интерфейс — статический локальный Web:

```text
HTML
CSS
JavaScript
```

Интерфейс должен работать в локальной сети без доступа к Internet.

Допускаются сторонние JavaScript/CSS-библиотеки только если одновременно выполняются условия:

- библиотека действительно полезна;
- её файлы хранятся локально в проекте;
- нет CDN/runtime Internet dependency;
- лицензия приемлема;
- библиотека работает в целевых браузерах, прежде всего Safari на iPad;
- добавление зависимости не создаёт неоправданной сложности.

Предпочтение отдаётся Vanilla JavaScript и стандартным Web API, если этого достаточно.

## 12. Целевой интерфейс и touch-first

Основное пользовательское устройство — iPad, установленный непосредственно в конференц-зале «Синий кит».

Следовательно:

- дизайн проектируется **touch-first**;
- основная ориентация — landscape;
- нельзя полагаться на hover как на обязательный способ взаимодействия;
- интерактивные зоны должны быть удобны для пальца;
- интерфейс не должен быть жёстко привязан к ровно `1024×768`;
- desktop browser является вторичной, но поддерживаемой средой просмотра;
- Safari/iPad compatibility является обязательной частью UI acceptance.

## 13. Разделение ответственности

### Web UI

Web отвечает за:

- отображение текущих состояний;
- пользовательские команды;
- touch UX;
- навигацию;
- локальное визуальное состояние интерфейса;
- позже — MQTT WebSocket transport и связь с WB/DMXWB.

Web **не должен быть основным местом автоматизации здания**.

### Wiren Board / WB Rules

WB Rules отвечают за:

- автоматизацию фанкойлов;
- автоматизацию вентиляции;
- режим проветривания;
- таймеры и возврат к предыдущему состоянию;
- взаимосвязи оборудования;
- виртуальные controls, необходимые Web.

### DMXWB

Существующий отдельный проект `Lex26p/DMXWB` отвечает за DMX512/Art-Net/MQTT модель освещения.

Blue Whale **не переписывает и не расширяет DMXWB без отдельного явного решения пользователя**.

Для Blue Whale DMXWB является внешней готовой подсистемой с MQTT API.

## 14. Старый проект Blue Whale

Старый Web/скрипты, предоставленные пользователем до начала нового репозитория, являются **только reference по смыслу системы и пользовательским идеям**.

Правила:

- старый код не переносится в новый проект;
- старые HTML/CSS/JS не являются foundation новой реализации;
- старые WB Rules не копируются автоматически;
- разрешено использовать идеи расположения, сценариев и UX;
- управление температурной уставкой намеренно может быть визуально близко к старому Web, поскольку это отдельно понравилось пользователю;
- новый код пишется с нуля.

## 15. Состояния утверждений

Для документации и обсуждения используются четыре состояния:

- **Confirmed** — доказано реальной проверкой, кодом, оборудованием или пользовательским acceptance;
- **Decided** — принято как требование или архитектурное решение, но ещё не обязательно реализовано;
- **Hypothesis** — рабочее предположение, требующее проверки;
- **Deferred** — сознательно отложено на будущий шаг/спринт.

Нельзя выдавать `Hypothesis` или `Decided` за `Confirmed`.

## 16. Документационная дисциплина

Нормативные документы:

```text
AGENTS.md
README.md
docs/TECHNICAL_SPEC.md
docs/ROADMAP.md
docs/PROJECT_STATE.md
```

Они должны обновляться вместе с развитием проекта.

Не создавать параллельные дублирующие документы без необходимости.

Если изменилось продуктовое требование — обновляется `TECHNICAL_SPEC.md`.
Если изменился порядок разработки или PASS — обновляется `ROADMAP.md`.
Если изменилась только текущая точка работы — обновляется `PROJECT_STATE.md`.
Если изменились правила взаимодействия — обновляется `AGENTS.md`.

## 17. Что не делать без отдельного решения

Не вводить в проект самовольно:

- React/Vue/Angular или другой framework;
- обязательный npm build;
- Internet/CDN dependency;
- отдельный backend только ради Web UI;
- Docker;
- WSL как обязательный development step;
- автоматизацию здания внутри браузера вместо WB Rules;
- прямую работу Web с Modbus-регистрами вентиляции;
- прямое управление физическим DMX-портом из Web;
- копирование старого проекта как foundation;
- изменение DMXWB из scope Blue Whale;
- избыточную security/enterprise-архитектуру для доверенного локального Web без реального требования.
